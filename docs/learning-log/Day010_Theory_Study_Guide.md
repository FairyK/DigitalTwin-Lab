## 2. 设备 ID 与 Actor 引用

### 2.1 三种东西不要混为一谈

收到的 MQTT 消息可能是：

``` json
{
  "device_id": "Motor02",
  "rpm": 1500,
  "temperature": 63.5,
  "running": true,
  "fault": false
}
```

这里的 `device_id` 是字符串，只表示"这条数据属于
Motor02"。它不会自动指向 UE 场景中的 Actor。

-   `BP_Motor`：蓝图类，描述电机对象的结构与行为。
-   场景里的 `Motor02`：一个具体 Actor 实例。
-   `Motor02Ref`：指向该实例的 UE 对象引用。
-   `"Motor02"`：消息中的文本标识。

所以必须建立映射：

``` text
"Motor01" → Motor01Ref → 场景中的电机实例
"Motor02" → Motor02Ref → 场景中的电机实例
```

### 2.2 为什么使用 Map

可以创建 `Map<String, BP_Motor Object Reference>`，以设备 ID 为
Key、Actor 引用为 Value。

若每条消息都遍历 N 个设备寻找目标，单次查找最坏情况是 O(N)。预先建立 Map
后，哈希映射的平均查找性能通常接近
O(1)，但实际性能仍取决于实现和数据规模。

### 2.3 Manager 的职责

`BP_MotorManager` / `BP_TwinManager` 可以负责：

1.  建立和维护设备 ID → Actor 引用的映射。
2.  接收已经解析好的设备数据。
3.  查找目标 Actor。
4.  检查 ID 是否存在、引用是否有效。
5.  调用目标的 `ApplyMotorData`。
6.  记录未知设备、无效数据和调试信息。

不要把网络接收、JSON 解析、设备映射、所有业务规则、UI
和材质逻辑都塞进一个巨大蓝图。

### 2.4 必须考虑的异常

-   未知 ID：例如 `Motor99` 没有登记。
-   无效引用：Actor 已销毁或引用失效。
-   重复登记：一个 ID 被映射到两个 Actor。
-   数据不完整：缺少字段或类型错误。
-   旧消息晚到：旧值覆盖新值。
-   设备离线：没有新消息，不代表设备必然停止。

**设备映射解决的是 UE 内部的对象定位，不是跨进程通信。** Python 和 UE
通常是不同进程，仍需插件、Socket、HTTP/WebSocket 或桥接程序把数据送进
UE。

## 3. 状态、事件、表现

### 状态 State：现在是什么

例如
`RPM = 1500`、`Temperature = 63.5`、`Running = true`、`Fault = false`。状态是当前事实，通常可反复读取。

### 事件 Event：发生了什么变化

例如电机从停止变成运行、首次进入故障、温度越过阈值、通信恢复。事件通常描述某个时刻发生的变化。

### 表现 Presentation：如何让人看懂

例如运行显示绿色、故障显示红色、停止显示灰色、温度超限显示告警文字。颜色不是故障状态本身；即使材质更新失败，`Fault = true`
仍应保留为明确的业务状态。

推荐逻辑：

``` text
接收数据 → 更新状态 → 判断是否发生变化
                         ├─ 有变化：广播事件
                         └─ 无变化：不重复广播同一事件
                         ↓
                    更新材质 / UI
```

如果 `Fault` 从 false 变成 true，这是"进入故障"；如果一直是
true，则不应每帧都重复广播"进入故障"。恢复时可以设计独立的
`OnMotorRecovered` 事件。

## 4. Function、Event Dispatcher、Delegate

-   **Function**：主动调用对象执行一个明确操作。例如
    `ApplyMotorData`、`ResetMotor`、`FindMotorByID`。
-   **Event Dispatcher**：对象发生事件时，通知已经绑定的监听者。例如
    `OnMotorFault` 通知 Manager、UI 或警示灯。
-   **Delegate**：更广义的可调用引用/回调机制。初学时先理解它与函数调用、事件广播的关系即可。

示意：

``` text
BP_Motor 广播 OnMotorFault
  ├─ BP_TwinManager：记录告警
  ├─ UI：显示故障
  └─ AlarmLight：改变表现
```

Dispatcher 是 UE 内部事件机制，不会自动把事件通过网络发送给 Python 或
MQTT。架构上，命令调用与事件通知表达的是不同方向的依赖。

## 5. Event Tick 与事件驱动

Tick 是 UE 在运行过程中按帧调用逻辑的机制。60 FPS 下，一帧约为：

\[ 1000 / 60 `\approx 16.67`{=tex}`\text{ ms}`{=tex} \]

这是整帧的时间预算，不是每个 Actor
的专属时间。渲染、动画、物理、蓝图等都要消耗它。

假设 3000 个 Actor 每帧都 Tick，60 FPS 下约为每秒 180,000 次 Tick
调用，尚未计算每次调用内部的节点成本。因此，不能把所有逻辑都放进 Tick。

适合事件驱动的工作包括：收到新数据时更新状态、故障变化时广播、用户按键时执行操作、离线计时器到期时检查状态。

网络上报频率与渲染帧率不是同一回事。设备可能每秒更新几次，而 UE
每秒渲染几十帧。画面通常只需读取合适时刻的最新状态；但报警、审计和历史分析可能要求保留每条采样，不能随意合并丢弃。

## 6. MID 与 MPC

### Base Material

基础材质 `M_Motor_Base` 可以公开 Vector Parameter，例如
`MotorColor`，供蓝图运行时改变颜色，而不必为每种颜色复制整份材质。

### MID：按对象动态修改

Material Instance Dynamic 是运行时可修改参数的材质实例。适合 Motor01
绿、Motor02 红、Motor03 灰等每台设备独立变化的需求。要确保修改的是目标
Mesh 上正确的 MID，而不是错误地共享了实例。

### MPC：共享参数

Material Parameter Collection
是多个材质可以读取的共享参数集合。适合全场景警报模式、统一环境色调或全局效果强度。

  需求                         通常更合适
  ---------------------------- -------------------------------
  只改变 Motor02 的故障颜色    MID
  每台电机颜色跟随自己的状态   按对象区分的 MID/材质参数方案
  全场景统一进入警报模式       MPC
  全场景统一调整环境效果       MPC

MID 与 MPC
不是业务状态数据库，也不保证天然更快；还要考虑材质槽、材质复杂度、阴影和渲染成本。

## 7. Hard Reference、Soft Reference 与异步加载

### Hard Reference

硬引用建立直接资源依赖。根据资源类型和加载路径，被引用资源可能随依赖链一起加载。优点是直接简单；风险是依赖链扩大后，可能增加加载时间和内存占用。

### Soft Reference

软引用主要保存资源路径/标识，允许在需要时请求加载。它不代表资源永远不加载，也不代表自动异步加载。

``` text
保存软引用路径
    ↓
需要时请求加载
    ↓
异步加载完成
    ↓
检查成功/失败
    ↓
使用资源
```

异步加载可以避免游戏线程同步等待大资源，但并非没有成本：磁盘
I/O、解压、资源创建和后续使用仍可能造成开销。要处理加载失败、重复请求、缓存和打包后的资源可用性。

## 8. MQTT 到 UE：跨进程与游戏线程

Python 的字典和 UE 的 Actor 不共享同一块进程内存。Python 收到 MQTT
消息后，UE
不会自动知道消息存在。需要明确的通信入口，例如插件、Socket、HTTP/WebSocket
或桥接程序。

推荐的概念流程：

``` text
MQTT Broker
   ↓
接收端 / 桥接程序
   ├─ 解析 JSON
   ├─ 校验字段、类型、单位
   ├─ 处理时间戳与序列号
   └─ 写入线程安全队列或最新状态缓存
                ↓
           UE Game Thread
                ↓
           查找设备 ID
                ↓
           ApplyMotorData
                ↓
           更新事件、MID、UI
```

UE 的许多 Actor、Component 和场景操作预期在 Game Thread
执行。网络回调若运行在其他线程，不应随意直接修改 Actor
或材质。通常让后台接收数据，再由游戏线程在安全时机消费数据并更新对象。

### 队列与最新状态缓存

-   **消息队列**：保留每条消息，适合不能丢失的事件和审计数据；如果生产速度大于消费速度，队列可能不断增长。
-   **最新状态缓存**：每个设备只保留最新值，适合画面显示；中间变化可能丢失，不能代替必须逐条保存的历史数据。

真实系统经常两者并用：当前状态用于显示，事件和历史采样另行可靠记录。

## 9. JSON 数据契约：解析成功不等于数据正确

可扩展的数据格式示例：

``` json
{
  "schema_version": 1,
  "device_id": "Motor02",
  "timestamp": "2026-10-13T10:30:00+08:00",
  "sequence": 1024,
  "rpm": 1500,
  "temperature_c": 63.5,
  "running": true,
  "fault": false
}
```

工程中应约定字段名称、类型、单位、时间格式和语义。建议检查：

-   `device_id` 是否存在且非空；
-   `rpm`、温度是否为数字并处于合理范围；
-   布尔字段是否真的是布尔值，而不是字符串 `"true"`；
-   时间戳格式、时区是否明确；
-   序列号是否重复或倒退；
-   接收端是否支持 `schema_version`。

单位错误尤其危险：摄氏度与华氏度的数字都能解析，但语义不同。时间戳也不能只用消息抵达
UE 的时间判断设备数据的新旧。

## 10. 从原型到工程系统的差距

  能力       原型               工程化需要
  ---------- ------------------ -----------------------------------
  设备映射   手动登记两个电机   动态注册、重复 ID、销毁与重连
  数据输入   键盘/模拟消息      断线恢复、重试、鉴权、协议兼容
  数据校验   基本字段检查       Schema 版本、单位、异常策略
  状态管理   当前变量           时间戳、序列号、离线与过期状态
  告警       颜色、打印文字     去抖、确认、恢复、历史追踪
  性能       少量对象验证       目标规模、帧率、CPU/GPU、内存指标
  资源管理   编辑器运行         异步加载、打包测试、失败回退
  可观测性   Print String       日志等级、指标、错误定位
  测试       手动验证           回归、压力、断线恢复测试

你目前的目标是建立一个可解释、可验证的小型数据驱动孪生原型，不是现在就完成全部工业工程能力。
