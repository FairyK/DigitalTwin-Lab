# Day008：设备身份映射与 UE 数字孪生对象管理

## 一、今日学习目标

今天围绕一个关键问题展开：

> MQTT 收到某台设备的数据后，系统如何找到 UE 场景中与它对应的 Actor，并更新正确的数字孪生对象？

今日重点：

- 区分跨进程通信与 UE 内部对象查找两个问题。
- 理解 `device_id`、Actor Reference、Map 和 `ApplyMotorData` 的关系。
- 初步理解设备管理器（Twin Manager）的职责。
- 将当天应做的 UE 实验完整记录为待办，之后有 UE 电脑时再集中补做。

## 二、今日学习的核心架构

```text
Python 设备模拟器
    ↓
JSON 数据
    ↓ MQTT Publish
Mosquitto Broker
    ↓ MQTT 转发
MQTT Subscriber / 数据接收层
    ↓
JSON 解析
    ↓
读取 device_id
    ↓
设备 ID → UE Actor 映射
    ↓
取得目标 Actor Reference
    ↓
调用 ApplyMotorData(...)
    ↓
更新 Temperature / RPM / Running / Fault
```

这条链路中有两个独立的问题：

1. **跨进程通信：** Python 与 UE 是两个独立运行的程序，内存相互隔离。Python 中的变量不会自动变成 UE Blueprint 中的变量，必须通过 MQTT、HTTP、WebSocket、TCP/UDP 等通信机制传输数据。
2. **对象映射与更新：** 数据进入 UE 后，UE 仍然需要知道它属于哪台设备，并找到对应 Actor，再调用该 Actor 的更新函数。

MQTT 解决消息传输问题，但不会自动替 UE 查找 `Motor01` 或 `Motor02`。

## 三、用 device_id 识别设备

示例消息：

```json
{
  "device_id": "Motor02",
  "rpm": 1800,
  "temperature": 72.5,
  "running": true,
  "fault": false
}
```

`device_id` 用于说明这条数据属于哪台设备。只有温度值，例如 `72.5`，并不能说明数据来自哪台电机。

当 UE 场景里有多个电机时，需要建立类似下面的映射：

```text
"Motor01" → Motor01 的 BP_Motor Actor Reference
"Motor02" → Motor02 的 BP_Motor Actor Reference
"Motor03" → Motor03 的 BP_Motor Actor Reference
```

真实设备 ID 与 UE Actor 的显示名称不必完全相同。更稳妥的设计是通过明确的映射关系关联两者，例如真实设备 ID `MTR-002` 可以映射到 UE 中的 `DigitalTwin_Motor_002`。

## 四、Actor Reference 与字符串的区别

- `"Motor02"` 是一个字符串，只是一个标识。
- `Motor02` 对应的 Actor Reference 是 UE 中实际对象的引用。
- 字符串本身不会自动变成对象引用，需要由查找逻辑或映射表建立联系。

可以把它理解为：

```text
device_id = "Motor02"
        ↓
查找映射表
        ↓
取得 Motor02 的 Actor Reference
        ↓
调用这个实例的 ApplyMotorData()
```

## 五、Map：通过 Key 查找 Value

UE Blueprint 的 Map 是一种键值映射数据结构，适合表达：

```text
Key (String) → Value (BP_Motor Object Reference)
```

例如：

```text
MotorMap
├── "Motor01" → Actor Reference 1
├── "Motor02" → Actor Reference 2
└── "Motor03" → Actor Reference 3
```

收到 `device_id = "Motor02"` 后，通过 Map 查找对应的 Actor Reference，再调用它的 `ApplyMotorData`。

注意：Map 只是保存“标识到对象引用”的映射，不会自动发现、注册或管理场景中的所有设备。映射表必须在初始化或注册过程中正确建立，并处理对象销毁、设备新增等情况。

## 六、统一更新接口 ApplyMotorData

`BP_Motor` 的统一数据更新函数规划如下：

| 输入参数 | 类型 | 更新变量 |
|---|---|---|
| `NewTemperature` | Float | `Temperature` |
| `NewRPM` | Float | `RPM` |
| `NewRunning` | Boolean | `Running` |
| `NewFault` | Boolean | `Fault` |

函数内部执行顺序：

```text
ApplyMotorData (Function Entry)
    ↓
Set Temperature  ← NewTemperature
    ↓
Set RPM          ← NewRPM
    ↓
Set Running      ← NewRunning
    ↓
Set Fault        ← NewFault
```

白色执行线控制节点执行顺序；彩色数据线传递具体参数值。

统一接口的意义在于：数据接入层负责接收和解析消息，电机 Blueprint 负责更新自身状态。未来数据可以来自 MQTT、OPC UA、REST API、ROS 2 或其他来源，而电机状态更新流程仍然可以复用。

## 七、找不到设备时如何处理

如果收到：

```json
{
  "device_id": "Motor999",
  "temperature": 80
}
```

但映射表中不存在 `Motor999`，就不能直接调用一个无效的 Actor Reference。

预期逻辑：

```text
Map Find
   ↓
是否找到？
 ├─ 是 → 检查引用有效 → 调用 ApplyMotorData
 └─ 否 → 记录未知设备 / 忽略 / 进入注册流程
```

实际项目还应考虑 Actor 已被销毁、数据格式不合法、字段缺失、数据过期和消息乱序等情况。

## 八、Twin Manager / 设备管理器

当设备数量增长时，不应让每个电机各自实现一套重复的设备查找逻辑。可以设计统一的设备管理器（例如 `BP_MotorManager`，后续也可以发展成更通用的 `BP_TwinManager`），负责：

- 注册设备与 Actor Reference 的对应关系。
- 根据 `device_id` 查找目标对象。
- 检查映射和对象引用是否有效。
- 将数据分发给目标数字孪生对象。
- 处理未知设备、重复注册和设备移除等情况。

逻辑结构：

```text
外部数据接收层
    ↓
解析 JSON
    ↓
提取 device_id
    ↓
Twin Manager
    ↓
Map Find
    ↓
目标 Actor Reference
    ↓
ApplyMotorData
```

这是一个初步架构。实际项目可以按规模采用 UE 内部管理器、后端服务维护设备注册表，或两者配合。

### UE-008-01：完成 BP_Motor.ApplyMotorData

**目的：** 验证统一状态更新接口。

1. 打开已有的 `BP_Motor`。
2. 创建或检查函数 `ApplyMotorData`。
3. 确认四个输入参数：

   - `NewRPM`：Float
   - `NewRunning`：Boolean
   - `NewFault`：Boolean
4. 在函数内部按顺序连接四个 Set 节点：
   - `NewTemperature` → `Set Temperature`
   - `NewRPM` → `Set RPM`
   - `NewRunning` → `Set Running`
   - `NewFault` → `Set Fault`
5. 编译并保存。

**验收标准：** 函数参数能够分别更新对应的四个变量。

### UE-008-02：用键盘事件模拟外部数据更新

1. 在 `BP_Motor` 的 Event Graph 中添加一个未占用的键盘事件（例如 `3`）。

3. 在调用节点设置测试值：
   - `NewTemperature = 75.0`
   - `NewRPM = 1500.0`
   - `NewRunning = true`

4. 编译、保存，进入 Play 并确保游戏视口获得焦点。
5. 按 `3`，检查变量或使用 `Print String` 验证调用结果。

**验收标准：** 当前 `BP_Motor` 实例的状态变成测试值。停止 Play 后数值恢复是运行时状态未持久化的正常现象。

### UE-008-03：建立 MotorMap

1. 先使用管理 Blueprint（暂定 `BP_MotorManager`）。
2. 创建 Map 变量 `MotorMap`。
3. Key 类型设为 `String`。
4. Value 类型设为 `BP_Motor Object Reference`。

**验收标准：** 变量结构可以表达设备 ID 到电机 Actor Reference 的映射。

### UE-008-04：注册 Motor01、Motor02、Motor03

1. 获取场景中三个 `BP_Motor` 实例的有效引用。
2. 将对应设备 ID 与 Actor Reference 写入 `MotorMap`。
3. 检查 Key 与 Value 是否配对正确。

**验收标准：** `Motor01`、`Motor02`、`Motor03` 三个 Key 分别指向正确实例。具体引用获取方式将在实操时根据项目结构选择，不预设必须采用某一种写法。

### UE-008-05：根据 device_id 查找并更新正确实例

1. 用 `DeviceID = "Motor02"` 作为测试输入。
2. 使用 Map 的 Find 操作查询 `MotorMap`。
3. 判断是否找到，并检查 Actor Reference 是否有效。
4. 找到后，对返回的目标引用调用 `ApplyMotorData`。
5. 设置一组明显的测试值，检查只有 Motor02 被更新。

**验收标准：** 数据目标由 `device_id` 决定，而不是固定写死为 Motor01。

### UE-008-06：处理未知设备 ID

1. 将 `DeviceID` 设置为 `Motor999`。
2. 执行 Map Find。
3. 对未找到的情况使用 Branch 处理。
4. 输出明确的调试信息，不调用无效引用。

**验收标准：** 未知设备不会导致无效对象调用；系统能输出可理解的诊断信息。

### UE-008-07：检查映射边界情况

后续扩展实验：

- 重复注册同一个设备 ID。
- 一个设备 ID 错误地关联到另一个 Actor。
- Actor 被销毁后 Map 仍保留旧引用。
- 新设备加入场景。
- 设备 ID 大小写、空格或格式不一致。

**验收标准：** 能解释这些情况可能导致的映射错误，并设计验证或纠错办法。

## 十一、今日总结

今天建立了以下认识：

- Python 和 UE 是独立进程，需要通信机制传递数据。
- MQTT 负责消息传输，不负责 UE 内部对象查找。
- `device_id` 标识设备；Actor Reference 指向 UE 中的实际实例。
- Map 可以保存 `device_id → Actor Reference` 的映射。
- `ApplyMotorData` 是统一的电机状态更新接口。
- Twin Manager 可以集中负责设备注册、查找、分发和异常处理。
- 未知设备与失效引用需要显式处理，不能假设每次查找都成功。
