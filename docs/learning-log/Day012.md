# 第一部分：工程原理——只讲本日真正需要的内容

## 1. 当前状态不等于刚刚发生的事件

假设电机的 `Fault` 是 Boolean：`false` 表示未故障，`true` 表示当前故障。

如果外部系统连续发送多条 `Fault=true`，这只能说明故障状态仍然存在，并不代表每条数据都产生了一次新的故障。如果每次都广播“故障发生”，可能出现重复弹窗、重复声音、告警计数错误和监听者重复执行。

因此，需要比较**更新前状态**与**更新后状态**：

| 旧值 | 新值 | 含义 | 是否广播“故障发生” |
|---|---|---|---|
| false | false | 仍然正常 | 否 |
| false | true | 刚刚进入故障 | 是 |
| true | true | 故障持续中 | 否 |
| true | false | 故障恢复 | 本日不广播故障发生事件 |

本日只处理 `false → true` 的边沿。将来可以单独增加 `OnMotorRecovered` 表达恢复，不要把故障发生和故障恢复混成一个事件。

### 必须遵守的执行顺序

1. 在覆盖状态前保存旧值；
2. 写入新状态；
3. 比较旧值和新值；
4. 只有 `旧值=false` 且 `新值=true` 时广播。

如果先执行 `Set Fault = NewFault`，再读取 `Fault` 作为旧值，读到的可能已经是新值，边沿检测就会失效。

## 2. Dispatcher 的工程风险在于绑定生命周期

Dispatcher 广播不会自动发现所有潜在监听者。监听者必须先绑定。要确认三个问题：

- **绑定时机：** 绑定是否发生在电机可能广播之前？早先发生的广播不会自动补发给后来绑定的监听者。
- **绑定次数：** 初始化路径是否可能执行多次？重复绑定可能让一次广播引发重复响应。
- **对象有效性：** 发出事件的电机和处理事件的 Manager 是否仍然有效？

本日只在初始化时绑定一次。不要把绑定节点放在 Tick 上。若监听者必须随时知道当前故障状态，应该读取当前状态或维护状态缓存，不能只依赖过去发生过的广播。

## 3. MID 的关键是实例隔离，而不只是颜色变化

基础材质 `M_Motor_Base` 定义共享的外观规则；动态材质实例 MID 允许在运行时修改参数。目标结构是：

```text
M_Motor_Base（共享材质规则，含 MotorColor 参数）
    ├── Motor01 → MID_Motor01（独立运行时参数）
    └── Motor02 → MID_Motor02（独立运行时参数）
```

验收重点：

- 修改 `Motor01` 不会改变 `Motor02`；
- 每个电机在初始化时创建自己的 MID；
- `MotorMID` 保存对应实例的动态材质引用；
- `Set Vector Parameter Value` 的参数名必须与材质中的参数名完全一致，例如 `MotorColor`。

### 初始化顺序

在 `BP_Motor` 的 `BeginPlay` 中，先从 `MotorMesh` 创建 MID，再保存到 `MotorMID`，最后调用 `UpdateMotorVisual`。如果在 MID 创建前更新颜色，`MotorMID` 可能为空，导致视觉没有更新。

## 4. 状态颜色需要明确优先级

本日规则：

1. `Fault=true` → 红色；
2. 否则 `Running=true` → 绿色；
3. 否则 → 灰色。

故障优先于运行状态。即使数据同时出现 `Fault=true` 和 `Running=true`，画面也必须显示红色。本日不加闪烁、声音、UMG 告警等效果，以免混淆问题。

# 第二部分：实验一——只在故障边沿广播事件

## 目标

`Fault` 从 `false` 变成 `true` 时广播一次；持续为 `true` 时不重复广播。

## A. 在 BP_Motor 中添加 Dispatcher

1. 打开 `Content/Blueprints/Motors/BP_Motor`。
2. 在 My Blueprint 面板新增 Event Dispatcher，命名为 `OnMotorFault`。
3. 本日先不添加参数。监听者可通过已有电机引用读取状态；后续需要统一告警时再考虑传入设备 ID、时间戳等参数。
4. Compile 并保存。

## B. 修改 ApplyMotorData 的 Fault 更新逻辑

保留原来更新温度、转速和运行状态的逻辑，只调整 Fault 相关部分。建议增加局部 Boolean 变量 `OldFault`。

```text
ApplyMotorData(NewTemperature, NewRPM, NewRunning, NewFault)
    │
    ├─ 读取当前 Fault → 保存为 OldFault
    ├─ Set Temperature = NewTemperature
    ├─ Set RPM = NewRPM
    ├─ Set Running = NewRunning
    ├─ Set Fault = NewFault
    └─ Branch: (NOT OldFault) AND NewFault
          ├─ True  → Call OnMotorFault
          └─ False → 不广播
```

操作注意：

- `OldFault` 必须在 `Set Fault` 之前读取。
- 条件是 `NOT OldFault AND NewFault`，不是只判断 `NewFault`。
- `OnMotorFault` 的调用节点只能放在 Branch 的 True 执行路径上。
- 不要为了这个实验重写整个 `ApplyMotorData`。

## C. 在 BP_MotorManager 中绑定

1. 打开 `BP_MotorManager`，找到现有的初始化流程。
2. 对 `Motor01` 和 `Motor02` 分别执行一次 `Bind Event to OnMotorFault`。
3. 为每个绑定节点创建 Custom Event，例如 `HandleMotor01Fault`、`HandleMotor02Fault`。
4. 每个事件先用 `Print String` 输出来源，例如 `Motor01 Fault`、`Motor02 Fault`，便于核对来源。
5. 确认绑定发生在任何测试更新之前。
6. 如果关卡里已有一个 Manager 实例，就使用该实例；不要在多个位置重复绑定同一台电机。
7. Compile 并保存。

**不要**在 Tick 中绑定，也不要为了确保监听成功而重复绑定。

## D. 验证矩阵

每一步都针对同一个电机实例，通过 `ApplyMotorData` 更新，并记录打印次数：

| 步骤 | 更新前 | 传入 Fault | 预期累计广播次数 |
|---|---:|---:|---:|
| 1 | false | false | 0 |
| 2 | false | true | 1 |
| 3 | true | true | 仍为 1 |
| 4 | true | true | 仍为 1 |
| 5 | true | false | 仍为 1 |
| 6 | false | true | 2 |

如果每次 Play 都重置了实例状态，请在同一次运行中完成一组测试，或清楚记录重新开始的边界。

## E. 失败排查顺序

1. `OnMotorFault` 是否已创建并 Compile？
2. `OldFault` 是否在 `Set Fault` 之前保存？
3. Branch 是否确实检查 `!OldFault AND NewFault`？
4. Manager 是否在测试前绑定了正确的电机实例？
5. 是否存在多个 Manager，或同一电机在多个位置被绑定？
6. 是否每次都重新启动关卡，导致状态被重置？

Vector Parameter: MotorColor
          │ RGB
          ▼
      Base Color

# 第四部分：实验三——为每台电机创建独立 MID

## 目标

每个 `BP_Motor` 实例在运行时创建并保存自己的动态材质实例。

## A. 添加变量

在 `BP_Motor` 中创建变量：

- 名称：`MotorMID`
- 类型：`Material Instance Dynamic` Object Reference

确认不是普通 Material，也不是 Material Instance Constant。

## B. BeginPlay 创建流程

在现有 `Event BeginPlay` 初始化流程中追加，不要创建互相独立的重复初始化链：

```text
Event BeginPlay
    ↓
Create Dynamic Material Instance
    Target = MotorMesh
    Element Index = 0
    ↓ Return Value
Set MotorMID
    ↓
Call UpdateMotorVisual
```

若节点提供 Target 参数，必须选择 `MotorMesh`；Element Index 使用正确的材质槽位，通常为 0。

## C. 验证实例隔离

先用临时测试逻辑给两台电机设置不同颜色：

- `Motor01`：蓝色；
- `Motor02`：黄色。

通过各自的 `MotorMID → Set Vector Parameter Value` 设置参数，Parameter Name 填 `MotorColor`。

**验收：** 两台电机颜色不同；修改其中一台不影响另一台；BeginPlay 后 `MotorMID` 有效。

若两台电机一起变色，优先检查是否修改了共享材质，或是否错误地共用了同一个 MID 引用。验证完成后删除临时颜色测试逻辑。

# 第五部分：实验四——让状态统一驱动画面

## 目标

把颜色规则集中到 `UpdateMotorVisual`，避免在多个函数中复制视觉逻辑。

## A. 创建函数

在 `BP_Motor` 中创建 Function：`UpdateMotorVisual`，无输入、无输出。

```text
UpdateMotorVisual
    ↓
Branch: Fault
    ├─ True  → ColorToApply = Red
    └─ False → Branch: Running
                 ├─ True  → ColorToApply = Green
                 └─ False → ColorToApply = Gray
    ↓
MotorMID → Set Vector Parameter Value
            Parameter Name = MotorColor
            Value = ColorToApply
```

颜色建议：

- 红色：R=1, G=0, B=0
- 绿色：R=0, G=1, B=0
- 灰色：R=0.35, G=0.35, B=0.35

可用局部 `ColorToApply` 变量，也可以让三个分支最终进入对应的设置参数节点。关键是优先级不能变：Fault > Running > Idle。

## B. 调用时机

1. `BeginPlay`：创建并保存 `MotorMID` 后调用 `UpdateMotorVisual`，同步初始状态。
2. `ApplyMotorData`：所有状态变量更新后调用 `UpdateMotorVisual`。
3. 故障边沿检测与广播应发生在状态已更新之后，确保监听者读取到的是新状态。

推荐顺序：

```text
保存 OldFault
    ↓
更新 Temperature / RPM / Running / Fault
    ↓
UpdateMotorVisual
    ↓
若 OldFault=false 且 NewFault=true → Call OnMotorFault
```

## C. 状态验证矩阵

| Fault | Running | 预期颜色 |
|---:|---:|---|
| false | false | 灰色 |
| false | true | 绿色 |
| true | false | 红色 |
| true | true | 红色（故障优先） |

分别对 `Motor01`、`Motor02` 测试，确认颜色独立，状态互不影响。

## 常见故障速查

| 症状 | 优先检查 |
|---|---|
| 故障事件从不触发 | 是否已绑定；是否调用 `ApplyMotorData`；边沿条件是否正确 |
| 每次 Fault=true 都触发 | 是否保存旧值；条件是否只判断了 NewFault |
| 同一次故障打印多次 | 是否重复绑定；是否存在多个 Manager；是否多处同时监听 |
| 电机一直显示默认颜色 | MID 是否创建；`MotorMID` 是否保存；`MotorColor` 名称是否一致 |
| 两台电机颜色一起变化 | 是否共享 MID；是否直接修改共享材质 |
| 初始颜色不正确 | 是否先创建 MID 再调用 `UpdateMotorVisual` |
| Fault=true 却显示绿色 | 分支优先级是否错误；Fault 分支是否优先 |
| 运行时正确、重启后失效 | BeginPlay 初始化是否完整；是否依赖上次运行的临时引用 |
