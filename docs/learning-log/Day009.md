### 2. 理解数字孪生的数据链路

```text
真实设备 / 仿真设备
        ↓
通信接入层：MQTT / OPC UA / HTTP / ROS 2
        ↓
数据处理层：解析、校验、时间戳、设备 ID
        ↓
孪生管理层：device_id → UE Actor Reference
        ↓
BP_Motor.ApplyMotorData(...)
        ↓
UE 场景表现：模型、材质、UI、告警
```

数据库、日志、监控和性能统计属于贯穿系统的支撑能力。将这些职责分层，可以降低模块之间的耦合，让通信方式或可视化方式变化时，不必推倒重写整个系统。

### 3. 区分状态、事件和表现

- **状态（State）：** 某个时刻的事实，例如 `Temperature = 85`、`Fault = true`。
- **事件（Event）：** 某件事发生或状态发生变化，例如故障从 `false` 变成 `true`。
- **表现（Presentation）：** 将状态或事件展示出来，例如电机变红、UI 告警或声音提示。

推荐思路：更新状态 → 判断是否发生变化 → 只在必要时广播事件 → 更新材质和 UI。避免每帧重复广播同一个故障事件。

### 4. 理解 Function、Event Dispatcher 和 Delegate

- **Function：** 明确地执行一项操作，例如 `ApplyMotorData`。
- **Event Dispatcher：** 向已绑定的监听者广播事件，例如 `OnMotorFault`。
- **Delegate：** 更广义的回调/函数引用机制；Event Dispatcher 是 UE 蓝图中常用的事件通知方式。

它们主要解决 UE 内部逻辑组织与通知问题，不会自动把事件发送到网络，也不会自动连接另一个进程中的 Python 程序。

### 5. 理解实时数据与线程边界

UE 的 Game Thread 负责大量 Actor、蓝图和场景更新工作。以 60 FPS 为例，每帧预算约为 16.67 ms。不要让游戏线程同步等待网络响应，也不要在任意后台线程直接操作 Actor/UObject。

推荐架构：

```text
网络接收 / 外部进程
        ↓
解析与校验
        ↓
线程安全队列或最新状态缓存
        ↓
Game Thread 消费数据
        ↓
更新 UE Actor
```

高频状态数据可以合并为“最新值”以减少更新压力；但如果业务要求每条采样都用于历史记录或告警判断，就不能随意丢弃中间样本。

### 6. 理解设备映射与规模化

设备 ID（例如字符串 `Motor02`）不是 UE Actor Reference。系统需要一个明确的映射层，把设备 ID 对应到场景中的孪生 Actor。

计划使用 `BP_MotorManager` 管理 `MotorMap`：

```text
"Motor01" → Motor01 Actor Reference
"Motor02" → Motor02 Actor Reference
```

使用 Map 按 ID 查找，通常比每条消息都遍历所有设备更合适。实际性能仍取决于实现方式和系统负载。设备映射解决的是数据分发问题；HISM、Merge Actors、Nanite、Lumen、VSM 和 Animation LOD 等则主要用于资源或渲染性能优化，不能互相替代。
